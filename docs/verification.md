# 検証と確認範囲

## 基本原則

検証は、実行したコマンド・確認日・環境に基づいて記録します。コードだけで確認できないデプロイ状態、GitHub 設定、実機動作、外部 API の応答を、未確認のまま「合格」や「稼働中」とは書きません。

## フロントエンドの品質ゲート

```powershell
npm run validate:data
npx tsc --noEmit
npm run build
npm run preview
```

| 確認 | 何を保証するか | 注意 |
|---|---|---|
| `npm run validate:data` | 時刻表、カレンダー、お知らせの構造・参照・不変条件 | `_examples/` は対象外 |
| `npx tsc --noEmit` | TypeScript の型、未使用ローカル・引数など | 実行時挙動は保証しない |
| `npm run build` | データ検証、型検査、Vite 出力 | `dist/` を作る |
| `npm run preview` | 本番ビルドのローカル表示 | PWA のキャッシュは実ブラウザで確認する |

ルートにはテスト・lint の npm スクリプトがありません。UI や PWA の変更では、コマンド結果だけでなく該当する手動確認を追加します。

## データ変更時の確認

- `calendar_rules.json` の override が実在日か、参照先の時刻表が存在するか
- `id` とファイル名、2 路線、時刻の形式・順序、座標、`note` が正しいか
- `closed` / `special` 以外の `schedule` を空にしていないか
- `special` と `closed` の表示意図を取り違えていないか
- `news.json` の HTML が信頼できる内容か、ID と未読フラグが正しいか
- 対象日を開き、片方向だけ・日付跨ぎ・終バス後など影響する画面を確認したか

詳細な検証器の対象は [data-model-and-operations.md](data-model-and-operations.md) を参照してください。

## PWA / 配信変更時の確認

- 通常起動で時刻表 JSON がネットワーク優先で取得される
- 更新ボタン後、オフラインにして再起動しても最新取得分が使われる
- 通信不能時に前回取得済みデータへフォールバックする
- 新 Service Worker をコールドスタート時と利用中で適切に扱う
- `dist/` に `_headers`、`_redirects`、マニフェスト、静的データが存在する
- iPhone / iPad、Android、デスクトップで、必要な表示・地図・PWA 導入を確認する

Cloudflare Pages の実デプロイ、HTTP ヘッダー、キャッシュ、Analytics は本番環境で別途確認します。確認できていない場合は、文書・リリース判断で未検証と明記します。

### 取得時刻とデータ状態の確認

`preview` は SW が有効なので、次を実ブラウザで確認します。`npm run dev` は SW が無効なため確認になりません。

| 状態 | 再現方法 |
|---|---|
| `offline` | 一度読み込む → DevTools の Network を Offline → リロード |
| `fetch-failed` | DevTools で `/data/*.json` を Block request URL に登録 → 更新ボタン |
| `no-data` | Application → Clear storage の後、上記をブロックした状態で初回アクセス |
| `stale` / `refetching-stale` | `/data/timetables/*.json` をブロックした状態で端末の日付を翌日へ進める。翌日分の先読みが成功していると昇格するので `stale` にならない |
| `stale-data` | 一度読み込んでキャッシュを作る → `localStorage.campusBusNaviFetchedAt` を 24 時間以上前の値へ書き換えてリロード。または OS はオンラインのまま `/data/` の応答だけを 3 秒以上遅延させ、キャッシュへフォールバックさせる |

### アクセシビリティ

| 確認 | 方法 |
|---|---|
| キーボードのフォーカスが見える | マウスを使わず Tab だけで一巡し、すべての操作要素にリングが出るか。タップで開いたオーバーレイにリングが出ないことも合わせて確認する |
| オーバーレイの隔離 | 初回のホーム画面追加案内（`MobilePwaGuide`）を出した状態で Tab を回し、背面のヘッダー・本文へ抜けないか。Escape で閉じて、元の位置へフォーカスが戻るか |
| 色のコントラスト | DevTools の computed style で `--text-muted` / `--past-text` とダイヤ種別バッジを実測し、[design-decisions.md](design-decisions.md) の表と一致するか。ライト・ダークの両方 |
| 更新の読み上げ | NVDA / VoiceOver で更新ボタンを押し、開始・成功・失敗が読み上げられるか。新しい Service Worker の検知バナーも同様 |

### 改修たたき台への忠実度（2026-09、原本再現パス）

`改修たたき台.dc.html`（1a バスタブ／2a 全時刻表シート／2b マップタブ／2c メニュータブ）に合わせて配色・寸法・構造を全面的に合わせ直したパス。`npm run dev` の実ブラウザ（390px 幅、ライト・ダーク両テーマ）で確認済み:

- バスタブ: ヘッダー（タイトル・更新ボタン・ルートトグル・日付ピル）、次のバスカード（円形ゲージ・残数バッジ・通知済みベル）、今後の発車時刻タイムライン（先頭行=次発の強調、以降4本）。`useJSTClock` を一時的に固定値へ書き換えて確認（要修正時は同じ手順で再現できる。本流のコードには残していない）
- 全時刻表シート: 上端58px開けたシート表示（背後のヘッダーが覗く・角丸）、日付ピル内のダイヤ種別バッジ、グリッドの現在便ハイライト（ルート色の面＋リング。この時点では両ルートとも緑。2026-09-11 のルート別テーマ色でルート追従に変更）・過去便・未来便の塗り分け
- マップタブ: ルートトグル、地図カード、ルート案内行、乗り場写真プレースホルダー、OSM 帰属表記（このマップタブの実装は2026-09-10に地図・Street ViewともGoogle埋め込みへ置き換わっており、この記述は置き換え前の状態の記録）
- メニュータブ: 個別カード行、外部リンクの斜め矢印アイコン、未読ドット。通知する便の指定は、バスタブの「発車前に通知」行から開く
- ボトムタブバーが `position: fixed` で画面下端に常時表示されること（メニュータブのように本文が長い画面でスクロールしても隠れない）
- ダークテーマ: 上記4画面を一通り確認し、視認できない組み合わせがないこと

**未確認・既知の制約:**
- 松永発（station）を選択中のルートトグルのアクティブ配色（グラデーション）は、原本のどのカットにも描かれていない（全カットが大学発選択中の状態）。大学発のグラデーションと同じ明度配分で類推した値（`RouteToggle.tsx` にコメントあり）で、原本との一致は確認できていない
- 実機（iPhone SE 等の小型端末、Android 実機）での確認は未実施。ブラウザのウィンドウ幅を狭めた確認のみ
- `DayBadge` のガラス演出廃止に伴うコントラスト値は計算上のみで、Chrome 実描画からの再計測（[design-decisions.md](design-decisions.md) がかつて行っていた `foreignObject` 手法）は行っていない。塗り色自体は変えていないため数値は理論上有効

### マップタブの Google 埋め込み化（2026-09-10）

地図・Street ViewをLeaflet+OSMからAPIキー不要のGoogle埋め込みiframeへ置き換えたパス（経緯は [design-decisions.md](design-decisions.md) を参照）。`npm run dev` の実ブラウザで、大学発・松永発それぞれの実データ座標で確認済み:

- 地図: 両ルートともピン付きの地図が正しい位置に表示される
- Street View: 大学発は実際のバス乗り場（バス・待合スペース）と一致するパノラマが表示された。**松永発は座標的に最寄りのパノラマが密集市街地内の無関係な店舗内観（美容室と思われる室内）に一致し、実際のバス乗り場とは異なる画像が表示された**（[design-decisions.md](design-decisions.md) に記載の既知の制約どおり）
- `npx tsc --noEmit`、`npm run build` とも成功。Leaflet依存除去によりプリキャッシュサイズが約900KiBから約730KiBへ縮小

**未確認・既知の制約:**
- Street Viewの座標最寄り検索は表示のたびに変わりうる可能性があり、今回確認した「松永発＝店舗内観」が常に再現するとは限らない（複数回の確認はしていない）
- 地図・Street Viewのオフライン非表示（クロスオリジンiframeのためService Workerキャッシュ不可）は、オフライン状態を作っての実機確認はしていない（挙動はコードの構造上明らかなため理論確認のみ）
- APIキー不要のGoogle埋め込み方式は非公式のため、将来Googleが変更・停止すると地図・Street Viewが両方表示されなくなる可能性がある（[design-decisions.md](design-decisions.md) 参照）

### 乗り場ピンと Street View パノラマの固定（2026-09-11）

上記「松永発＝店舗内観」の解消として、Street View をルート別の `panoid` / `heading` / `pitch`（`src/utils/buildEmbedUrl.ts` の `STREET_VIEW_SPOTS`）で固定し、松永発のピン座標を修正したパス（経緯は [design-decisions.md](design-decisions.md)、手順は [data-model-and-operations.md](data-model-and-operations.md)）。

`output=svembed` のパラメータ挙動は、値だけを変えた iframe を並べた検証ページ（プロジェクト外）を Chrome で開いて比較した:

- `panoid` 単独指定で狙ったパノラマが出る。`heading` と `pitch` も効く（`pitch` は正が下向き）
- `panoid` と `cbll` を同時に付けると意図しない別パノラマになった → 併用しない
- 存在しない `panoid` を渡すと座標最寄りにフォールバックした
- ズームは指定できない: `cbp` の4番目は向きのオフセットとして働き、`cbp` の3・6・7番目、`fov` / `zoom` / `cbz` / `svz` クエリは無視、新形式 URL（`/maps/@…,3a,30y,…?output=svembed`）は表示不能
- Google マップ URL の `130t` を開くと上向きになり、埋め込みで同じ向きにするには `pitch=-40`（= 90 − 130）だった

確定値は、アプリと同じ大きさ（358×326px）のカードで地図と Street View を並べた調整ページで、利用者が Google マップから座標と URL を貼って目視で選んだもの。反映後 `npm run validate:data`・`npx tsc --noEmit`・Bot の `npx vitest run`（198件）と `npx tsc --noEmit` が成功。

**未確認:**
- 反映後の `npm run dev` およびスマートフォン実機での表示は、この記録時点では未確認
- `pitch` は調整ページのプレビュー（埋め込みそのもの）で見た向きをそのまま採用しているが、調整ページの初版は Google マップ URL からの `pitch` 読み取り符号が逆だったため、URL を貼っただけで目視確認していなければ上下が逆の可能性がある（実機確認で要チェック）

### 実機実測フィードバックの反映（2026-09-10）

iPhone のホーム画面 PWA での実測スクリーンショットをもとに 6 件を修正したパス。`npx tsc --noEmit` と `npm run build` は成功。`npm run dev` の実ブラウザ（Chrome）で確認済み:

- 地の白統一（`--bg-page` = `#ffffff`）: バス／マップ／メニューの3タブ、全時刻表シート、設定、ヘルプ、お知らせ、週間ダイヤを一通り表示し、白地に溶けて見えなくなったカードが無いこと。ダークテーマ（`html.dark`）でも同様に確認
- ホームの日付ピルが `9/10（木）` 表記になり、右端に `›` が出ること。全時刻表シート内の日付ピルも同じ表記に揃っていること（こちらは表示専用でタップできないため `›` は付けない）
- マップタブの経路案内リンクの `href` が `www.google.com/maps/dir/` であること（DOM で確認）
- ボトムタブバーの `padding-top` が 6px（原本の 9px から 3px 上げ）であること、`getBoundingClientRect().bottom` が `window.innerHeight` と一致すること
- ビューポート短縮の補正が PC ブラウザでは発動しない（誤補正が起きない）こと

**実機で棄却した対処（2026-09-10）:**
- 最初の実装は「ズレたぶんタブバーを負の `bottom` でビューポート外へ押し下げる」補正でしたが、実機（iPhone 16 Pro / ホーム画面 PWA）で**タブバーのアイコンとラベルが消えました**。iOS が `position: fixed` の描画をレイアウトビューポートでクリップするためです。スクリーンショットのピクセル実測で、押し下げた未読ドットが 812pt（= 短いビューポート高）でちょうど切れていることを確認し、原因を特定しました。この方向の補正は不可です（[design-decisions.md](design-decisions.md) に警告を記載）。
- 現在は `recoverShortViewport()`（viewport メタを書き換えて WebKit にビューポートを再評価させる）に置き換えています。

**実機の結果（2026-09-10）:**
- `recoverShortViewport()` により、ボトムタブバーが画面下端まで届くようになりました。
- ただし当初は `main()` の中（待機 SW 確認の await 後）で呼んでいたため、**起動のたびにタブバーが一度高い位置に描かれ、0.5 秒弱で正しい位置へ跳ぶ動きが見えました**（0.5 秒は待機 SW 確認の `Promise.race` のタイムアウトと一致）。モジュール評価時（React マウント前）の呼び出しへ移しています。
- **メタの書き換えでは 6pt 足りません。** スクリーンショットのピクセル実測で、起動直後はビューポート 868pt（実画面 874pt）、スクロールまたはタブ切替の後に 874pt になることを確認（[design-decisions.md](design-decisions.md) に表として記載）。アイコン塊のサイズは両状態で同一（116 デバイスpx）のため、拡大縮小ではなく平行移動と判定。
- **書き換えを繰り返しても 868pt から動きませんでした**（繰り返し＋マウント後の 2 巡目を入れた版を実機で確認）。解消するのはスクロールまたはタブ切替の時点のみで、単なるタップでは直りません。
- **1px スクロールを足した最初の版も効きませんでした。** 原因は実装のバグで、`scrollTo(0, 1)` と `scrollTo(0, 0)` を同じフレームで続けて呼んでいたため、ブラウザに合成されて `y=1` でのレイアウトが一度も起きていませんでした。
- **同じ問題を持たない既存プロジェクト（`ToDo-Reminder`）の実装を参照して解決方針を定めました。** 差分は 2 点で、(1) 1px スクロールを次のフレームで戻すこと、(2) `min-height: 100lvh` で文書が実画面ぶんの高さを保ちスクロール可能であること。こちらは `min-height` に実測値（`--app-height`）を使っていたため、ビューポートが短いときは文書も短くなりスクロールできない状態でした。両方を取り込んでいます（[design-decisions.md](design-decisions.md) 参照）。

- **参照実装に合わせた版（次フレームでの戻し＋`100lvh`）で解消を実機確認しました（2026-09-10、iPhone 16 Pro / ホーム画面 PWA）。** 起動直後からタブバーが画面下端まで届き、その後スクロールやタブ切替をしてもズレません。

**未確認・既知の制約:**
- 確認は iPhone 16 Pro のみです。他機種・iPad・Android では確認していません
- `body { min-height: 100lvh }` を足したことで、ビューポートが短い状態では文書がその差分（最大 62pt 程度）だけスクロールできるようになります。正常時は `100lvh` = ビューポート高なので余分なスクロールは発生しません
- 参照プロジェクトの viewport メタには `shrink-to-fit=no` がなく、この差自体が原因である可能性は未検討のまま残っています（外すと iPad の縮小不具合が再発しうるため触っていません。現在の対処で解消しているため、外す必要は生じていません）
- マップタブ・メニュータブのヘッダーに足した `env(safe-area-inset-top)` は、PC ブラウザではインセットが 0 のため見た目が変わらず、ノッチ機での重なり解消は実機確認が必要です
- iOS で Google マップ URL が「アプリが入っていればアプリ、無ければブラウザ」で開くことは実機未確認です

### バスタブの「発車前に通知」行を常時表示にした変更（2026-09-11）

たたき台 1a の「発車前に通知」行は実装済みでしたが、描画条件が `push.status === 'subscribed'` だったため、通知が未購読の端末では行そのものが出ていませんでした。常時表示に変え、未購読時は理由を出して設定画面へ導く形にしたパス（[design-decisions.md](design-decisions.md) 参照）。`npx tsc --noEmit` と `npm run build` は成功。`npm run dev` の実ブラウザ（Chrome、`Notification.permission` が `default` = `idle` 状態）で確認済み:

- バスタブのタイムライン直下に行が出る。説明は「オフ ・ タップして通知をオンにする」
- その行をタップすると設定画面が開き、「発車リマインダー」トグル（オフ）が見える
- 行の見た目（38px のベルアイコンチップ、角丸16px、右端の `›`）がたたき台 1a と一致する

**未確認・既知の制約:**
- 確認できたのは `idle`（未購読）の分岐だけです。`subscribed`（`N 件設定中 ・ M分前` ／ `未設定` ／ 読み込み中 ／ 読み込み失敗）、`ios-needs-install`、`denied`、`unsupported` の各表示は、実際にその状態を作っての確認をしていません。`subscribed` の確認には配信サーバ（`/api/*`）と実機の購読が要ります
- 行は従来どおり `!isEndOfService && nextBus` のブロック内にあるため、終バス後・全便運休日・特別ダイヤの日には出ません（たたき台 1a に「今後の発車時刻」セクションごと無い状態のカットが無いため、この場合の扱いは原本と照合できていません）
- ダークテーマでの表示は確認していません（配色は既存の `--menu-group-bg` / `--slot-current-bg` などのトークンをそのまま使っており、新しい色は足していません）

### テーマトークンと押下状態

- ライト／ダークの両方で、通知時刻の選択文字とベル印が `--route-accent-fg`、戻る・選択チェック・スピナーが `--ui-accent-fg`、通知状態・エラー本文が `--status-*-fg` に追従すること。アイコン用 `--icon-*-fg` を本文へ戻さない。（`--accent-fg` は 2026-09-11 に廃止し、ルート依存の用途と中立の用途へ分割した。`--route-tint-*` はトークンとしては残っているがコンポーネントからの参照は無い。）
- お知らせは未読／既読／押下でそれぞれ `--news-unread-bg`／`--bg-card`／`--row-active` になり、未読が太い片側線ではなく「未読」ラベルでも伝わること。
- メニュータブの行、ニュースカード、FAQ 行を pointer down／up／leave／cancel で確認する。押下が他の行へ連動せず、スクロール開始やキャンセルで残らないこと。
- Tab、Enter、Space で既存のフォーカスリング・操作・ニュース詳細からのフォーカス復帰が保たれること。外部リンクは `<a>` のままであること。

### 通知（便の同定）

| 確認 | 方法 |
|---|---|
| 予約した便と通知が一致する | 実機で便を予約し、届いた通知の時刻・方向が予約と一致するか。**逆方向や別時刻が出たら不具合** |
| 同定できないときの挙動 | 予約が無い状態で `server/tools/send-test-push.ts` から 1 通送り、「まもなく発車です／アプリを開いて時刻表を確認してください」になるか |
| 通知オフで写しが消える | オフにしたあと DevTools の Application → IndexedDB で `campusBusNaviPush` が空になっているか |

### 週間ダイヤの確認

- 同じ日について、ホームの `DayBadge` と週一覧のラベルが完全に一致する
- Network タブで、同じ時刻表 ID の日が複数あってもリクエストは ID ごとに 1 回だけ
- 週間ダイヤを連打で開閉しても、古い応答が後から表示されない
- `timetable_closed` の日に時刻が出ず「運行なし」、`timetable_special` の日に時刻が出ず大学ホームページへの誘導が出る
- `/data/timetables/` の 1 ファイルだけを Block request URL に登録し、その日だけ「取得できません」になり、他の日のダイヤで代用されない
- 当日を開いたときだけ過去便が灰色になり、他の日は全便が同じ濃さ
- ホームの日付ピル（タップで週間ダイヤを開く）と、メニュータブの「週間ダイヤ」行の両方から開けるか
- 日付跨ぎで当日分が未取得（`stale`）の間、ホームの日付ピル（週間ダイヤへの入口を兼ねる）が表示されない

```js

for (const req of await c.keys()) {
  const res = await c.match(req)
  console.log(new URL(req.url).pathname, res.headers.get('date'))
}
```

通知条件を変更した場合は、少なくとも次の境界をユニットテストで固定します。

- 過去日の管理 override 削除だけなら `calendar_cleanup_only=true` 相当になる

最後の条件は `.github/workflows/timetable-sync.yml` の二重確認です。ローカルのユニットテストだけでは GitHub Actions の step output とメール action の配線までは保証できないため、`main` 反映後の実走で確認します。

ワークフローが適用前に通す検証器と同じものを、リポジトリ直下でも実行できます。


OCR、実ファイル書込、GitHub Actions での自動適用とメール送信を伴う確認は、必要な権限・鍵がそろった人間管理下で段階的に実施します。

#### Cron 経由の通知が届かない（2026-08-18 調査。原因特定済み、対処は未実施）

2026-08-18（`timetable_vacation_summer_weekday`。運休日でも特別ダイヤでもない日）に iPhone のホーム画面 PWA から 3 便へ通知を設定したところ、**1 通も届きませんでした。** 同日 16:46 JST の `/api/status` は次を返しています。

```json
{ "devices": 1, "remindersToday": 3, "sentToday": 0, "pendingToday": 3,
  "staleReminders": 0, "overdueReminders": 3 }
```

**原因: 配信 Worker がデプロイされたまま更新されておらず、現在の D1 スキーマと噛み合っていません。**

`npx wrangler deployments list` で確認した最後のデプロイは 2026-08-15T18:51:05Z（= 2026-08-16 03:51 JST）で、これは `server/src` の変更履歴では commit `5867b85` の時点です。その約 1 時間後の `8b90b41` / `e7888d5`（2026-08-16 04:56）で、リマインドは「端末ごとに 1 件の常設予約」から「当日の便ごとの `reminders` 行」へ作り直されています。デプロイ済みの Worker が毎分実行しているのは変更前のクエリです。

```sql
SELECT * FROM subscriptions WHERE last_sent_on IS NULL OR last_sent_on != ? LIMIT ?
```

現在の `subscriptions` に `last_sent_on` 列は無いため、D1 が `no such column` を返し、`run()` が throw、`scheduled` が再 throw します。**2026-08-16 04:56 以降、Cron は毎分失敗し続けています。**（`VAPID_PRIVATE_KEY` は `npx wrangler secret list` で登録済みを確認。鍵は原因ではありません。）

対処は Worker の再デプロイです。**人間が実行します。**

```powershell
Set-Location server
npx wrangler deploy
```

デプロイ後の確認:

1. `npx wrangler tail` を出したまま 10 分程度先の便へ通知を設定し、`送信対象 N 件 / M バッチ` のログと実機の受信を確認する
2. `/api/status` の `sentToday` が増えることを確認する
3. 翌日、`staleReminders` が 0 のままであることを確認する（毎時 00 分の掃除が動いている証拠）

なお、発車時刻を過ぎた `overdueReminders` は `selectDue` の窓（`[発車 − リード分, 発車)`）を外れているため、デプロイしても遡って送信されることはありません。

#### この乖離が起きる構造

**Pages は `git push` で自動反映されますが、配信 Worker は `npx wrangler deploy` を人間が実行するまで古いままです。** `server/src/schedule.ts` は `src/utils/diagramType.ts` と `src/types/timetable.d.ts` を直接 import しているため、フロントエンド側の変更でも Worker の再デプロイが要る場合があります。D1 のスキーマを変えたときは、**migration の適用と Worker のデプロイを必ず同じ作業でまとめてください。**
