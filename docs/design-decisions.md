# 重要な設計判断

この文書は、見た目の好みではなく、誤案内、更新不能、モバイル上の破綻を避けるための設計判断をまとめます。変更時は「現在のコードを短くできるか」だけでなく、ここに書かれた失敗モードが再発しないかを確認してください。

## 安全性に関わる判断

| 判断 | 現在の実装 | 変える場合に確認すること |
|---|---|---|
| 時刻は JST | `useJSTClock` が `Asia/Tokyo` を返す | UTC や端末ローカル時刻が混ざらないこと |
| 次発の境界 | `departure > 現在分`。同じ分の便は通過済み | 秒単位表示へ変える場合も発車瞬間の扱いを定義すること |
| 日付跨ぎ | 対象日を保存し、古いデータでは `stale` 表示にする | 前日の時刻を当日の見出しで出さないこと |
| 特別ダイヤ | 時刻を推測せず、大学公式ページへ誘導する | `special` を `closed` より先に判定すること |
| 全便運休 | 空 `schedule` と `closed` ID で表す | `special` と同じ空配列でも意味を混同しないこと |
| JSON キャッシュ | 通常起動は NetworkFirst、データはプリキャッシュしない | 更新後に古いビルド時 JSON が優先されないこと |
| 取得時刻 | `Date` レスポンスヘッダを根拠にする。`Date.now()` を既定にしない | オフラインでキャッシュから読めただけの成功を「取得」と数えないこと |
| 本文の鮮度 | 取得成功でも 24 時間以上前の本文なら帯で伝える（`stale-data`） | 「取得できた」と「その本文が新しい」を混同しないこと |
| 壊れた時刻表 | `closed` / `special` 以外で全便が読めなくなったら `throw` する | 破損を「運行なし」と逆案内しないこと |
| ダイヤ種別バッジ | `stale` 中と時刻表未取得時は描かない | 実データを見ずに種別を名乗らないこと |
| 通知の便の同定 | 端末の写しと突き合わせ、一致しなければ便を断定しない | 受信時刻から次の便を推測しないこと |

### 「推測するより表示しない」

一部の便しか読み取れない、運休と運行が混在する、片方向の時刻しか確定できない、といった場合に、既存ダイヤを補完して表示してはいけません。`timetable_special` は、利用者が存在しない便を信じることを防ぐための状態です。

この原則は Bot の `needs_review` にも適用されます。期間を正しく読める未確定掲示は特別ダイヤで安全側に塗りますが、非実在日や逆転した期間は誤読の可能性が高いため塗りません。Bot の正確な規則は `BACKEND_REQUIREMENTS.md` を参照してください。

### 日付跨ぎ

日付が変わると、表示中データが即座に正しい当日分になるとは限りません。オフライン、低速回線、23:59 に始まったリクエストが日付変更後に完了する競合を考慮する必要があります。

`useTimetable` は翌日を先読みし、一致する場合だけ当日分へ昇格します。そうでない場合は再取得完了まで時刻を隠します。このガードと `seqRef` の世代確認を外さないでください。

翌日分の取得と `normalizeTimetable()` は両方まとめて `catch` します。先読みはあくまで日付跨ぎ用の保険なので、翌日ファイルの形式不正で当日の表示まで落としてはいけません。

### 週間ダイヤを 7 日で打ち切る

`overrides` は先の日付まで入っていますが、連続しているのは 2026-08-15 時点で 2026-09-23 までで、その先は祝日が飛び飛びに入っているだけです。上限を「`overrides` の最終日」にすると、10 月以降が `default_rules` 由来の「授業日ダイヤ」で埋まり、まだ公表されていない長期休暇ダイヤを授業日として見せることになります。

大学の掲示が確定している範囲をデータから判定する手段はないため、当日起点 7 日の固定窓にして、末尾に「表示できるのは 7 日先までです。予定は変更されることがあります。」と添えています。日数を伸ばす場合は、この誤案内の経路を別の方法で塞いでから行ってください。

週間ダイヤでも「推測するより表示しない」は同じです。取得できなかった日は前後の日のダイヤで埋めず、その日だけ「取得できません」と出します。

ダイヤ種別のラベルと色は `DayBadge` をコンポーネントごと置いて表示します。色を写し取った第二の定義を作らないためです。

### 取得時刻は「fetch が成功した時刻」ではない

`fetch` の成功は「サーバから新しいデータが返った」ことを意味しません。オフラインでも SW の NetworkFirst が `timetable-data` キャッシュへフォールバックするため `fetch` は解決します。ここで素朴に `Date.now()` を入れると、数日前のデータに「たった今取得」と表示してしまいます。これはオフライン時にこそ嘘になるため、鮮度表示の意味がなくなります。

そこで `resolveFetchedAt()` は次の順で判断します。

1. `Date` レスポンスヘッダが読め、妥当な範囲（端末時計の前後 5 分／30 日以内）なら、それを採用する。Cache API はレスポンスをヘッダごと保存するので、キャッシュから返った場合でも「実際にサーバから返ってきた時刻」が残る
2. 読めない場合、`navigator.onLine === false` なら `null` を返し、呼び出し側が前回値を維持する（オフライン中の成功を「取得」と数えない）
3. それ以外は `Date.now()`

`public/_headers` は `/data/*.json` に `no-store` を付けていますが `Date` は落としていません。ヘッダを落とす設定を足すと、精度がフォールバック経路まで下がります。

値は `campusBusNaviFetchedAt` に保存し、`Date` ヘッダが読めない環境でもオフライン起動直後に前回セッションの取得時刻を出せるようにしています。アプリ初期化で消えるのは正しい挙動です。

表示は相対と絶対の併記（「3時間前に取得（8/17 07:12）」）で、`formatFetchedAt()` が `now` を引数で受けるため `useJSTClock` の毎分更新に追従します。独自タイマーは持ちません。端末時計の巻き戻しなどで差分が負になった場合は `null` を返し、呼び出し側は行ごと描きません。

「最新」とは言いません。言えるのは「取得した」ことだけです。

### 取得成功でも古い本文なら黙って出さない

SW の NetworkFirst は、ネットワークが 3 秒で応答しないと `timetable-data` キャッシュ（最大 7 日保持）へ**成功として**フォールバックします。`navigator.onLine` が true で `fetch` も例外を投げないため、何もしないと最大 7 日前のダイヤを通常表示のまま最新として見せます。

そこで `deriveDataStatus()` は、他の状態に該当しない場合でも `fetchedAt` の経過を見て `stale-data` を返します。閾値は **24 時間**です。時刻表の更新は Bot の日次実行（07:00 JST）で入るため、24 時間以上前の本文は「1 回以上の更新機会を跨いだ」と確実に言えます。

時刻自体は隠しません（オフラインでの可用性を落とさないため）。ヘッダー直下の帯（`StatusBand`）で「表示中の時刻表は最新ではない可能性があります」と取得時刻を添え、再取得の導線を出すところまでが役割です。

閾値を変える場合は、Bot の実行時刻（`.github/workflows/timetable-sync.yml` の cron）と SW の `maxAgeSeconds`（`vite.config.ts`）との関係を見直してください。

### 全便が読めなくなった通常ダイヤを「運休」と言わない

`normalizeTimetable()` は不正な `departure` を落として表示を続けます。一部が壊れていても読める便は見せるためです。ただし**全件落ちたときは意味が変わります**。空 `schedule` は運休日・特別ダイヤ専用の表現なので、そのまま返すと `App` が「本日の運行はありません」と断定してしまいます（配信後の破損・キャッシュ破損を運休と逆案内する）。

`scripts/validate-data.mjs` は追跡データに対して同じ規則でビルドを止めています。`normalizeTimetable()` はその規則をランタイムにも置いたもので、`closed` / `special` 以外で正規化後に空になった route があれば `throw` します。呼び出し側（`useTimetable` / `useWeekTimetables`）は既に catch して「取得できません」へ落ちます。

## PWA とキャッシュ

- `data/**/*.json` は Workbox のプリキャッシュから除外します。除外を外すと NetworkFirst が通常起動で実質無効になります。
- `/data/` の URL パターンは、更新ボタンの `?t=` を許す末尾 `(?:\?.*)?` 相当を持ちます。
- `timetable-data` というキャッシュ名は Vite 設定と `useTimetable` の双方で使います。片方だけの変更は、手動更新後のオフライン表示を壊します。
- 更新通知は prompt 型です。セッション中にアプリを強制更新せず、コールドスタート時だけ自動適用します。
- 更新ボタンが使う `?t=` 付きのエントリは、素の URL へ書き戻したあとに削除します。削除しないと押すたびに一意のエントリが増え、`maxEntries` に達したときにオフライン起動が頼りにしている素の URL のエントリが押し出されます。SW 側の `cache.put` と競合して消し損ねうるので、枠自体も 60 件に広げてあります（best-effort と余裕の二段構え）。

詳細は [pwa-and-deployment.md](pwa-and-deployment.md) を参照してください。

## iPad / モバイル表示

### iPad Safari の縮小対策

`index.html` の `shrink-to-fit=no` は、iPad Safari / PWA が一瞬の横幅超過を契機にレイアウト幅を拡大し、画面全体を縮小してしまう問題への対策です。`dvh` や倍率固定、`viewport-fit` の変更はこの問題の修正本体ではありません。

### レスポンシブの境界（廃止）

2026-09 の3タブ構成への改修で、PC / 横向き専用の2カラム表示（`main.tsx` の `syncBpActiveClass`、`html.bp-active`、`@custom-variant bp`）は廃止しました。画面幅に関わらず常に同じ縦1カラムのタブ構成（バス／マップ／メニュー）で表示する方針に統一したためです。地図カードが固定高になり、以前あった「左カラムの高さに地図を追従させる」ロジック（`bp:min-h-[300px]` 等、当時はLeafletの`MapContainer`が対象）は不要になりました。地図の実装自体はその後さらにGoogle埋め込みiframeへ置き換わっています（[上の節](#地図と-street-view-の埋め込み方式apiキー不要)を参照）。

この判断を変更する場合（PC 向けに別レイアウトを再導入する場合）は、上記の高さ追従ロジックが解決していた問題（文字サイズ設定で左カラムの高さが 441 / 497 / 539px と変わる、地図を固定高にすると下端がずれる）を再度検討してください。

### オーバースクロール

JavaScript でタッチ移動を乗っ取り、疑似的なバウンスを作る方式は採用しません。実機の慣性スクロールと競合したためです。

- iOS / iPadOS はネイティブのラバーバンドを解放し、上端の色は `.header-cushion` で連続させます。
- Android 等の粗いポインタ端末はネイティブのストレッチを使い、スクロール連鎖と pull-to-refresh を抑えます。
- PC はバウンスなしです。

2026-09 の3タブ構成への改修でヘッダーは白基調（`--bg-card` の単色）になり、`.header-cushion` も同じ単色を敷くだけになりました。以前あった「ヘッダーのグラデーション停止位置をクッションの90degグラデで近似する」計算（`useNativeBounce.ts` の座標変換）は、単色になったことで不要になり削除しています。ヘッダーに再びグラデーションを使う場合は、この近似計算を復元する必要があります。

下端の露出域は `body` 背景（`--bg-page`）が塗ります。同月の白基調化（後述の「ライトテーマの地は白」）でこれがボトムタブバーの `--bg-card` と同色になったため、ライトでは露出が目立ちません。ダークは `--bg-page` と `--bg-card` が別値のままなので、下端バウンスでタブバーより暗い面が覗きます（意図した挙動）。

### 全時刻表シートのスクロールとグラバー

全時刻表シートは上端 58px を残す部分オーバーレイで、背面はドキュメントスクロールのまま残ります。2026-09 の実機報告に合わせて次のようにしています。

- **開いている間は背面（`body`）のスクロールを止めます**（`useBodyScrollLock`）。止めないと、シートの非スクロール領域（グラバーやヘッダー）を指でなぞっただけで背後のホームが動きます。iOS ではルートのバウンスを解放している（上の「オーバースクロール」）ぶん、背面がよく動く状態にあります。手段は `overflow: hidden` **と** `position: fixed`（`top` に現在のスクロール量を負で指定）の併用です。iOS のタッチスクロールは `overflow: hidden` だけでは確実に止まらないため、body を流れから外して「そもそもスクロールできる高さを持たせない」形にします。`top` を指定するので見た目は動かず、解除時に `window.scrollTo` で元の位置へ戻します。`position: fixed` の子（シート・タブバー・クッション）は transform を持つ祖先がない限りビューポート基準のままなので影響を受けません。本文スクローラ側の `overscroll-behavior: contain` は連鎖抑止として残します。
- **タイトルと閉じるボタンは本文と一緒にスクロールさせます。** スクローラの外に固定していたとき、シートを下に引っ張ると本文だけがバウンスして見出しだけ取り残されて見えました。
- **上グラバーは装飾ではなく、下へ引いて閉じるハンドルです**（`useSheetDragToClose`）。指で掴む対象なので、当たり判定は見た目の横線（36×5）ではなく横いっぱい・上下の余白込み（高さ約 27px）で取り、`touch-action: none` を付けてハンドル上での既定スクロールを止めます。**タップでは閉じません** —— 読んでいる途中の誤タップでシートが消えるのを避けるためで、閉じる操作は×ボタン・背景タップ・Escape・下ドラッグ（80px 超）です。ドラッグ中だけインラインの `transform` で `.sheet-panel` のトランジションを上書きし、離したときに閉じる（`translateY(100%)`）か元へ戻す（インライン解除）かを決めます。インライン指定は閉じアニメ終了後、または次に開くときに必ず消します（残ると次回シートが出てきません）。

### ボトムタブバーが画面下端から浮く（iOS PWA、初回起動）

実機（iPhone 16 Pro、ホーム画面に追加した PWA）で、起動直後の 1 回だけ `position: fixed; bottom: 0` のボトムタブバーが画面下端から上部セーフエリアぶん浮くことがあります。レイアウトビューポート（`fixed` の基準になる initial containing block）の高さが「実画面高 − 上部セーフエリア」で確定してしまうためで（実測 874pt に対し 812pt）、ページ自体は画面上端から描かれるので下端に約 62pt の帯が残ります。初回に起きやすいのは、待機中サービスワーカーを適用するために `main.tsx` が一度 `location.reload()` するためと考えられます。

⚠️ **タブバーを負の `bottom` でビューポート外へ押し下げる補正は行わないでください。** 一度これを実装しましたが、**iOS は `position: fixed` の描画をレイアウトビューポートでクリップする**ため、はみ出したアイコンとラベルが丸ごと消えました（2026-09-10 実機で確認。押し下げた未読ドットが 812pt でちょうど切れていた。枠と境界線だけが残り、中身が無いタブバーになる）。**ビューポートの外にページは何も描けません** —— 画面全体を塗るのはルート背景だけです（初回の症状で下端の帯が `--bg-page` 色に見えていたのはこのためです）。

現在の対処は `main.tsx` の `recoverShortViewport()` で、ビューポート自体を直す方向です。`screen.height`（全画面の iOS PWA では実画面高と一致するのが正しい）と、`fixed; bottom:0` のプローブ要素で測ったビューポート下端を比べ、短ければ viewport メタの `content` を一瞬だけ別の値（`initial-scale` を `1.0001` に）へ書き換えて次フレームで戻し、WebKit にビューポートを再評価させます。判定は「iOS かつ standalone かつ `innerWidth` が画面幅と一致」に限り、ズレが 1px 以下または 120px 超なら何もしません。1 セッション 1 回だけ試みます。実機（2026-09-10）でタブバーが画面下端まで届くようになることを確認しました。

⚠️ **開始はモジュール評価時（`main()` の待機 SW 確認より前、React のマウントより前）です。後ろへ動かさないでください。** 当初は `main()` の中で呼んでいたため、起動のたびにタブバーが一度短いビューポートの位置に描かれ、0.5 秒ほど遅れて正しい位置へ跳ぶのが見えていました（実機で報告あり。0.5 秒は待機 SW 確認の `Promise.race` のタイムアウトと一致します）。タブバーが最初に描かれる前に是正が終わっていれば、動きは見えません。

⚠️ **1 回の書き換えでは足りません。** 実機のスクリーンショットをピクセル実測した結果（2026-09-10、iPhone 16 Pro / 実画面 874pt）:

| 状態 | タブバー上端 | バー下端 = レイアウトビューポート高 |
|---|---|---|
| コールドスタート直後（是正前） | 736pt | 812pt（62pt 不足） |
| 1 回書き換えた後 | 792pt | 868pt（6pt 不足） |
| ユーザーがスクロール／タブ切替した後 | 798pt | 874pt（正しい） |

アクティブタブのアイコン塊のサイズは 3 状態とも同一（116 デバイスpx）で、拡大縮小ではなくバーが平行移動しているだけです。

**メタの書き換えを繰り返すだけでは 868pt から動きませんでした**（実機で確認済み）。残り 6pt が解消するのはユーザーが**スクロール**または**タブ切替**をした時点で、**単なるタップでは直りません**。

決め手になったのは、同じ構成のボトムナビを持ちながらこの問題が起きない既存プロジェクト（`C:\Users\mote1\dev\ToDo-Reminder`）の実装でした。要点は 2 つです。

**(1) 1px スクロールして「次のフレームで」戻す。** 参照実装は `load` → `requestAnimationFrame` → `scrollTo(0, 1)` → `requestAnimationFrame` → `scrollTo(0, 0)` という形をとっています。

> ⚠️ `scrollTo(0, 1)` と `scrollTo(0, 0)` を**同じフレームで続けて呼んではいけません**。ブラウザが合成してしまい、`y=1` でのレイアウトが一度も起きず完全な無操作になります。こちらの実装が効かなかったのは、まさにこれが原因でした（2026-09-10）。

**(2) 文書がスクロールできる高さを持っていること。** 参照実装は `html, body, #root` に `min-height: 100lvh` を敷いています。`lvh` はブラウザ UI の出入りで変わらない側の高さなので、レイアウトビューポートが一時的に短く確定しても文書は実画面ぶんの高さを保ち、その差分だけスクロールできます。こちらは `min-height` に実測値（`--app-height`）を使っていたため、**ビューポートが短いときは文書も同じだけ短くなり、そもそもスクロールできない状態**でした。`index.css` の `body` に `min-height: 100lvh` を足して前提を揃えています（アプリシェル側の `--app-height` は iPad 対策としてそのまま）。

現在の 1 パスは「スペーサーで文書に高さを与える → viewport メタを書き換える → `scrollTo(0, 1)` → **次フレーム**で `scrollTo(0, 0)` とメタ・スペーサーを戻す」で、これを **収束するまでフレームごとに繰り返し**（上限 `MAX_RECOVERY_PASSES`）、**`load` 時**と **React のマウント後**にも測り直します。ズレが 0 になった時点で `measureViewportShortfall()` が 0 を返して即座に止まります。メタの書き換えを残しているのは、単独で 62pt の不足を 6pt まで詰める効果が実測できているためです。

**この形で解消を実機確認しました**（2026-09-10、iPhone 16 Pro / ホーム画面 PWA。起動直後から下端まで届き、その後の操作でもズレない）。

**未検討**: 参照プロジェクトの viewport メタには `shrink-to-fit=no` がありません（こちらは iPad の縮小対策として付けています）。この差自体がビューポートが短く確定する原因である可能性は残っていますが、外すと iPad の縮小不具合が再発しうるため、この対処では触っていません。

この再評価が効かなかった場合でも、タブバーはビューポート下端（`bottom: 0`）に居るので中身が消えることはありません。残る帯はルート背景が塗り、ライトテーマでは `--bg-page` がタブバーの `--bg-card` と同じ白なので目立ちません（ダークは 2 色が別値のままなので、暗い帯が覗きます）。

## オーバーレイとアクセシビリティ

全時刻表シート、お知らせ、設定、ヘルプは開閉アニメーションのため、閉じた後も DOM に残ります。`useOverlayA11y` は以下を担います。

- 閉じた画面、または他の画面に覆われた画面を `inert` にする
- 開いた直後に最初の操作要素へフォーカスを移す
- 閉じた後に呼び出し元へフォーカスを戻す
- Escape で閉じる

React 18 では `inert={false}` が属性文字列として残ることがあるため、`inert` は JSX 属性でなく DOM プロパティとして設定します。背面も `App` でまとめて `inert` にします。

`MobilePwaGuide`（初回のホーム画面追加案内）も `aria-modal` を名乗るため、開閉状態は `App` が持ち、背面の `inert` 対象（`anyOverlayOpen`）に含めます。案内自体は背面レイヤーの**外**に置きます。中に置くと自分も `inert` の対象になり、「背面だけを隔離する」が成立しません。

### フォーカスリング

`:focus` は `outline: none` のままにし、`:focus-visible` に自前のリングを定義しています。

- `:focus` を消すのは、タップでオーバーレイを開くと `useOverlayA11y` が内部の最初の操作要素へフォーカスを移すため、押した覚えのないものに青枠が出て見えていたからです
- `:focus-visible` はブラウザが「キーボード等の起点」と判断したときだけ当たるので、上の問題を起こさずにキーボードの現在位置を示せます
- リングは二重（内側 `--focus-ring` = `outline` / 外側 `--focus-ring-alt` = `box-shadow`）です。フォーカスは濃い面にも淡い面にも載るため、片方の色だけでは一方の地で消えます
- `border-radius` は指定しません。`outline` は要素自身の角丸に沿うので、丸ボタン（ハンバーガー・更新）にも正しい形で付きます

⚠️ **`--focus-ring`（`outline` 側）だけで成立する色を選んでください。** ヘッダーのアイコンボタンなど、inline style で `box-shadow` を持つ要素では外側リングが inline に負け、`outline` しか描かれません。

実測値（非文字要素の要件は 3:1）:

| 地 | ライト `#111827` | ダーク `#f9fafb` |
|---|---|---|
| `--bg-page` | 17.74 | 16.98 |
| `--bg-card` | 17.74 | 14.05 |
| `--bg-input` | 15.62 | 9.86 |

⚠️ 上表からヘッダー上端の行（旧・松永発グラデ `#7c87f0` / 旧・大学発グラデ `#0d9966`）を削除しました。2026-09 の3タブ構成への改修でヘッダーは白基調の単色（`--bg-card`）になり、ルート別のグラデーションヘッダー自体が廃止されたためです。彩度のある青（一度採用しかけた `#1d4ed8`）がヘッダー上で要件を満たさなかった、という経緯の記録として残しますが、現行のフォーカスリングは `--bg-page` / `--bg-card` / `--bg-input` 上でのみ機能を確認すればよく、上表の残り3行がそれに当たります。

両方を `outline: none` に戻してはいけません。キーボード利用者が自分の位置を一切把握できなくなります。

## テーマと操作フィードバック

- テーマは `light` / `dark` / `system` で、React マウント前にも同じ localStorage キーを読んで `html.dark` を同期します。キーや判定を片方だけ変えてはいけません。
- 全要素のタップハイライトを消しているため、押下状態は `usePressable` で管理します。iOS Safari で信頼できない `:active` だけに戻さないでください。
- `tapFeedback()` は触覚フィードバックを一箇所へ集めています。iOS Safari で Vibration API が無反応でも異常ではありません。
- `RouteSwitch`（`WeeklyScreen` が使う、ページ面用）はトラックの余白 3px・`gap` なしの 2 分割・ノブ幅 `calc(50% - 3px)` が対です。`gap` を足すとノブ位置が崩れます。
- 配色を変更する場合は合成後のコントラストを再測定し、適合状況を明記してください。
- 2026-09 の3タブ構成への改修で `RouteToggle` は半透明ガラス（`.frost-surface`、ヘッダーのグラデが透ける前提の面）から、`--bg-input` トラック＋塗りつぶしノブの方式に変わり、さらに改修たたき台への移行（同月内）で今の形（`--pill-track-bg` のトラックに `gap:4/padding:5`、選択中のボタン自体がグラデーション＋白ボタンアイコンになる方式。共有の「スライドするノブ」要素は持たず、各ボタンが自分の active/inactive をそれぞれ描く）になりました。ページ面にも直接置けるため、`RouteSwitch` との役割分担（ヘッダー用/ページ面用）は薄れていますが、`RouteSwitch` は独自の溝・落ち影表現を持つ別コンポーネントとして残っています。
- 週間ダイヤの土日の色（`--dow-sat` / `--dow-sun`）は、行の面が `--bg-card` と `--bg-card2` の 2 種類あるため、淡い方でも AA を満たす値にしてあります。赤に `#dc2626` を使うと `--bg-card2` 上で 4.48:1 と割ります。状態を伝える文字（運行なし・時刻なし・取得できません）は赤ではなく `--chip-text` で、色ではなく語で伝えます。これは `StatusCard` と同じ判断です。
- 状態を**本文**で伝える `--status-success-fg` / `--status-danger-fg` と、線アイコン用の `--icon-*-fg` は用途を分けます。後者を12px前後の本文へ流用すると、ライトテーマで必要なコントラストを満たさない値があります。
- 未読お知らせは太い片側の線ではなく、`--news-unread-bg` の控えめな面差と「未読」ラベルで伝えます。お知らせ画面内のピルは `--news-unread-accent` を使います。ボトムタブバーとメニュータブの未読ドットは、改修デザインで新設した `--menu-unread-fg`（`#0ea5e9` 系）を使う別トークンで、意味（未読があること）は共有しますが色は独立しています。
- 行全体を操作するメニュータブ・お知らせ・FAQ は、押下中だけ `--row-active` にし、離すと `background 0.3s` で戻します。`usePressable` の pointer 操作を使い、iOS Safari で不安定な `:active` だけには戻しません。キーボード操作の現在位置は既存の `:focus-visible` が担います。

### ライトテーマの地は白（`--bg-page` = `#ffffff`）

改修たたき台（`.sample/改修たたき台.dc.html`）は 4 画面（ホーム／全時刻表シート／マップタブ／メニュータブ）とも `.scr { background:#fff }` で、地とヘッダー・タブバーが同じ白で連続します。実機で見ると従来の `#f2f3f7` は「原本に無い薄いグレー」として目立つため、2026-09 にライトの `--bg-page` を白へ変更しました（ダークは変更していません。原本はライトのみのデザインのため）。副作用として次を合わせています。

- **`.header-plain` の下境界線を削除**しました。原本のヘッダーブロックは区切り線を持たず、ヘッダーは sticky ではなく本文と一緒にスクロールするため、線が無くても本文と重なりません。
- **ページ面に置く白いカードは輪郭を足しました。** 白地に `--bg-card`（白）のカードを置くと面として立たないため、設定・ヘルプ・お知らせ（既読）・週間ダイヤの行には `inset 0 0 0 1px var(--row-card-border)` のヘアラインを敷いています。`border` ではなく inset の影にするのは、行の内側余白と行高を 1px も変えないためです（`.section-card::after` と同じ考え方）。カードの塗り自体は変えていないので、上表以下のコントラスト測定値はそのまま有効です。
- 影と落ち影で輪郭を作る `.section-card` / `.hero-card` は元から地と同系の白面を前提にしているため、変更していません。

### 色のコントラスト

WCAG 2.1 AA の通常文字は 4.5:1、非文字要素と large text（18.66px 以上の bold、または 24px 以上）は 3:1 です。

**ダイヤ種別バッジ（`DayBadge`）は「半透明の色をダーク面へ合成した結果」を 1 色として持ちます。** 一度は不透明の濃色へ差し替えて AA を満たしましたが（8aa8349）、見た目が重くなるため半透明の明るい色へ戻し、そのうえで色付きガラスの意匠に変えました。改修たたき台（2026-09）への移行では、原本が単色フラットのバッジしか描いていないため、**ガラスの意匠（上端ハイライト・内側の光のリング・同色の落ち影）は廃止し、下記の塗り色そのままのフラット表示**にしています。塗りの色自体は変えていないため、以下の測定はそのまま有効です。

このとき、半透明のままだと**同じバッジがテーマと面によって違う色に見えます**（ダーク面では濃く締まって見え、白面では白に薄まる）。そこで、はっきり見えていたダーク面での合成結果 `rgba(基色, α − 0.08)` over `#1f2937` を計算し、その色を不透明の塗りとして両テーマで使っています。結果としてライトとダークで見えが揃い、行の面が 2 種類（`--bg-card` / `--bg-card2`）あっても値がブレません。

| 種別 | 塗り | 白文字とのコントラスト |
|---|---|---|
| weekday | `#346bc4` | 5.19 |
| holiday | `#b93d41` | 5.52 |
| vacation | `#c19711` | 2.73 |
| vacation_weekday | `#0f6d94` | 5.78 |
| vacation_holiday | `#b23367` | 5.89 |
| event | `#c7621e` | 4.04 |
| closed | `#5a616f` | 6.22 |
| special | `#884bcb` | 5.36 |

**`vacation` はまだ WCAG AA の通常文字 4.5:1 を満たしません**（13px bold は large text の 3:1 の基準にも掛かりません）。ガラス表現時代の半透明のままだった頃の 1.78〜3.60 よりは上がっていますが、見た目を優先した判断であることを承知して選んでいます。一段暗くすれば AA に届きます。

`vacation_weekday` / `vacation_holiday` の 2 種だけは、上の「半透明をダーク面へ合成した値」ではなく、**直接選んだ不透明色**です。長期休暇中のダイヤは中身が平日・休日の運行そのものなので、色も `weekday` / `holiday` の同系（deep blue / deep rose）に寄せ、色相をずらして別種と分かるようにしています。CIELAB の ΔE\*ab は `weekday` から 33、`holiday` から 27 で、同系と分かる近さと、隣り合っても取り違えない差の両方を取っています。`event`（橙）・`special`（紫）・`closed`（灰）とはいずれも ΔE 50 以上離れています。合成由来ではないぶん白文字とのコントラストも自由に選べたので、元になった `weekday`（3.41 / 5.19）・`holiday`（3.72 / 5.52）より高い値にしてあります。ラベルは「平日ダイヤ（長期休暇）」「休日ダイヤ（長期休暇）」で、色と同じく「平日／休日の運行が主、長期休暇は但し書き」という並びに揃えています。

**同系色に寄せたぶん、色だけに頼る見分けは弱くなっています。** 色覚特性のシミュレーション（Viénot 1999 の 2 色型変換）で測ると、`weekday` と `vacation_weekday`、`holiday` と `vacation_holiday` はいずれも P 型・D 型で ΔE 27〜28 と保たれますが、T 型では ΔE 4〜5 まで縮みます。黄土色だった頃（P/D/T 型で 118/129/69、44/29/31）より確実に近くなっており、これは「同系色に寄せる」という判断の代償です。バッジは必ずラベル文字を伴うため、色だけが識別の手掛かりになる場面はありません。なお既存の配色にはこれより深刻な近接（D 型で `weekday` と `special` が ΔE 2）が元からあり、逆に旧配色では 2 種の長期休暇バッジ同士が全型で ΔE 12〜14 とほぼ同色でした（現在は 16〜92）。

配色を変えるときは、必ずこの比を測り直してください。白文字のまま AA を満たすなら塗りをさらに濃くする、淡い面のままなら白文字をやめて同系の濃色文字にする、のどちらかになります。

補助文字のトークンも直しました。

| トークン | 旧 | 現在 | 実測 |
|---|---|---|---|
| `--text-muted`（ライト） | `#aaaaaa`（2.10〜2.32） | `#666c79` | page 4.75 / card 5.27 / card2 4.89 |
| `--text-muted`（ダーク） | `#6b7280`（3.04） | `#9ca3af` | card 5.78 / page 6.99 / card2 6.22 |
| `--past-text`（ライト） | `#cccccc`（1.53） | `#666c79` | `--past-bg` 上で 5.00 |
| `--past-text`（ダーク） | `#4b5563`（2.09） | `#7c8595` | `--past-bg` 上で 4.24 |

過ぎた便（`--past-text`）のダークだけは 4.5 を狙わず、非文字要素と同じ 3:1 を確実に超える値にしています。過ぎた便は補助情報で、淡さ自体が「もう乗れない」という情報だからです。淡さは面（`--past-bg`）と字の細さで保ちます。

**意図的に AA を外している箇所**は、ライトテーマのルート切替ラベル（上の項）だけです。配色を変えるときは、`backdrop-filter` を含む合成後の値を測り直し、この表を更新してください。

## 地図と Street View の埋め込み方式（APIキー不要）

2026-09、マップタブの地図（従来 Leaflet + OpenStreetMap）とStreet View（従来は写真プレースホルダー）を、`maps.google.com` の埋め込みiframe（`src/utils/buildEmbedUrl.ts`）に置き換えました。

**Google Cloud 公式の「Maps Embed API」ではなく非公式方式を採用した理由**: 公式APIはAPIキー発行にGoogle Cloudへの支払い情報登録が必須ですが、この登録ができないという制約がありました。代替として `maps.google.com/maps?...&output=embed`（地図）・`output=svembed`（Street View）という、Web版Googleマップが古くから提供している無登録の埋め込み方式を採用しています。実際にブラウザで動作検証済み（2026-09時点）ですが、Googleの公式ドキュメントに載っていない非公式な方式のため、**将来Googleが予告なく変更・廃止する可能性があります**（ただし少なくとも2014年頃から現在まで安定して動作している実績があります）。

**受け入れたトレードオフ**:
- オフライン時に地図・Street Viewが表示されない（クロスオリジンiframeのためService Workerでキャッシュ不可。従来のOSMタイルCacheFirstキャッシュは失われた）
- カスタムピン・ツールチップ・ルート切替時のスムーズなアニメーションはなくなり、Google純正のUIになる
- Street Viewは座標（`bus_stop_coords`）から最寄りのパノラマを自動検索して表示するため、**必ずしも実際のバス乗り場が写るとは限らない**（検証時、密集市街地の停留所で無関係な店舗内観に一致した例を確認済み）。より正確に表示するには、`buildEmbedStreetViewUrl` の `heading` 調整だけでなく、Googleマップ上で該当パノラマを直接探して `panoid` を指定する形への変更が必要になる場合がある

カードの縁と影は `src/index.css` の共通クラス・変数で管理します。コンポーネント側に同じ影を直書きし始めると、テーマや地図カードとの整合が崩れます。


## 発車前の通知（Web Push）

- **アプリ内で鳴らす通知は持ちません。** 通知が要るのはアプリを閉じて発車時刻を忘れているときで、開いている間だけ鳴る機能は本当に必要な場面を救わないためです。画面内にできるのは「設定済みの便に印を付ける」ことだけです。
- **`.ics`（カレンダー連携）ではなく Web Push を採ったのは、通知の送り主をアプリ名にするためです。** `.ics` は追加インフラなしで動きますが、通知は「カレンダー」から届きます。ネイティブアプリ化（ローカル通知）も検討しましたが、ストア審査・Mac・配布方式の変更がコストに見合いませんでした。
- **通知の許可は 2 段階です。** 設定画面のトグルが端末の登録（通知の根幹の許可）を担い、そのあとで「本日の全時刻表」から便を指定します。順序は UI だけでなくサーバ側でも守り、未登録の端末からの指定は 409 で拒みます。
- **バスタブの「発車前に通知」行は、通知がオフでも隠しません。** 2 段階目（便の指定）だけを持つ行なので購読済みのときだけ出す実装にしていましたが、それだと未購読の利用者には機能の存在自体が見えず、設定画面を開くまで通知があると気づけません。行は常に出し、購読済みなら本日の予約状況（`N 件設定中 ・ M分前`）を見せて全時刻表シートへ、未購読ならその理由（オフ／iOS はホーム画面追加が必要／拒否済み／非対応）を見せて設定画面へ導きます（`REMINDER_OFF_TEXT`）。到達条件を誤解させない原則は変えていません。届かない状態で「設定できる」とは書かず、理由と次の一手だけを出します。
- **購読済みでも、サーバの予約を読めていない間は「未設定」と書きません。** `useDepartureReminders` の `loadState` をそのまま行の説明に反映し、`loading` は「設定を読み込み中...」、`error` は「設定を読み込めませんでした」を出します。読めていない状態を 0 件と言い換えると、実際には予約があるのに無いと信じさせます。時刻表側の「推測するより出さない」と同じ判断です。
- **リマインドは当日限りです。** ダイヤは日によって変わるため、翌日以降の便を先に予約させません。`reminders.date_key` により、Cron の抽出・日付変更時の掃除・クライアントの取り直しのすべてが当日ぶんに閉じます。
- **時刻表のマスは選択モードのときだけボタンになります。** 常時タップ可能にすると、時刻表を読むだけの指やスクロール中の誤タップが予定を作ります。通常時は `div` のままです。
- **運休日・特別ダイヤ・ダイヤ差し替えで消えた便には送りません。** 「推測するより出さない」という時刻表表示の判断を、通知でも同じく適用しています。判定は `src/utils/diagramType.ts` の `resolveDiagramType` をフロントとサーバで共有し、命名規約の解釈が二重定義にならないようにしています。
- **送信判定は「ちょうど N 分前」の等号一致ではなく窓で行います。** Cron の実行が遅れると等号一致では取りこぼすためです。詳細と無料枠に由来する制約（ペイロードなし push、Durable Object での分配）は [backend-push.md](backend-push.md) にあります。
- **通知に載せる便は、端末に写した予約と突き合わせて決めます。受信時刻から次の便を推測しません。** ペイロードなし push には予約の同定情報が載らないため、推測すると予約した便より前の便や逆方向の便を断定してしまいます。写しが無い・当日でない・当日のダイヤにその便が実在しない場合は、便を断定せず「まもなく発車です」に落とします。時刻表側の「推測するより表示しない」と同じ判断です。
- **通知を設定できるのは当日ぶんだけで、これはサーバ側の時計で判定します。** 当日限りという仕様であると同時に、無認証 API から未来日を無限に登録して D1 の書き込み枠を枯渇させる経路を塞ぐためでもあります。
- **通知をオフにしたとき、サーバ側の削除に失敗したら端末の購読も解除しません。** 端末だけ解除すると、画面は「オフ」なのに D1 に情報が残り、README の「預かっている情報はすべて削除されます」と食い違います。
- **通知許可のダイアログは、ユーザーがトグルを押したときにだけ出します。** 起動時に勝手に要求しません。iOS Safari のタブでは `Notification` 自体が未定義のことがあるため、参照はすべて `typeof` で守ります。
